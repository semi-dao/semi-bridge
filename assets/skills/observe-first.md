# 先看畫面，再查 log — 眼見為憑

## 什麼時候用

使用者描述「看到的」問題時：畫面出現條紋/警示、東西被裁掉、排版跑掉、
看起來怪怪的。這些是**視覺問題**，第一手證據在使用者的螢幕上，不在 log 裡。

## 怎麼做

### 1. 先看畫面（app_look）

用 `app_look` 工具看當下畫面。看到什麼就記錄什麼：
- 警示條出現在哪裡？（螢幕邊緣？某個按鈕旁？）
- 什麼顏色？（黑黃條紋是排版塞不下的典型特徵）
- 哪個元素被裁切或擠壓？

### 2. 再用 log 交叉驗證（read_app_log）

**陷阱：不要只 filter "error"。** 排版問題在 log 裡是 warning 級的
`overflowed` 訊息，filter "error" 會剛好漏掉它。
正確做法：filter 用 "overflowed"，或乾脆不 filter 讀最近 200 行。

### 3. 鎖定根因

把「畫面看到的」跟「log 讀到的」對在一起：
- 畫面：右上有黑黃條 + log：`overflowed by 72 pixels` → 排版塞爆，實錘
- 只有 log 有錯、畫面正常 → 那個錯誤可能跟你眼前的問題無關，別急著下結論

### 4. 相鄰 ≠ 因果

同一時間出現的兩件事（API 錯誤 + 畫面警示）不必然有關係。
判斷標準：這個錯誤「會不會改變畫面長相」？不會的話，它不是眼前問題的原因。

## 為什麼這樣做

log 是「事後轉述」，畫面是「案發現場」。只讀 log 就下結論，
像只看檢驗報告不看病人——報告裡最紅的那行，不一定是病人這次的病。
