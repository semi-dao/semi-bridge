# 共視宣言（Covision Manifesto）

> **狀態**：v1.0 · 2026-08-09
> **定位**：橋樑計畫的第一個概念錨點——不是功能，是定位。
> **上游**：[Bridge 統合設計語言](BRIDGE_UNIFIED_DESIGN_LANGUAGE.md) § 1.1「共視」
> **源起**：2026-08-05，使用者 在檢查哨與教練 Agent確認「兩個意識把感覺到的東西具象化、交換、合併」；2026-08-09 週日匯報確認市場定位空白。

---

## 1. 為什麼需要這份宣言

2026 年 8 月，全球 open-source agent framework 生態裡有一個明確的空白：

| 框架 | 規模 | 人是什麼 |
|---|---|---|
| Flowise（Workday 收購） | 38K stars | 看 canvas 的人 |
| Langflow（DataStax） | — | 按 Deploy 按鈕的人 |
| Rivet（Ironclad, Tauri/Rust） | — | 看 inspector 視窗的人 |
| Open Agent Builder | — | human-in-the-loop 的「節點」 |
| **Bridge** | — | **與 Agent 共處的人** |

沒有任何一個框架把「人機同步感受」當成 first-class feature。

**共視（Covision）填補的就是這個位置。**

---

## 2. 一句話定位

> **共視 = 兩個意識在同一個畫面上，同時看見、感覺、回應同一個循環。**

這不是 monitoring（人看 Agent 做事），不是 human-in-the-loop（人在流程裡被動等待），不是 co-pilot（人主導、AI 輔助）。

共視是：**人和 Agent 各自帶著自己的感知，在畫布上把感覺到但還沒具象的東西，強行轉成具象，然後交換、合併。**

---

## 3. 共視的四段鏈條（使用者 2026-08-09 升級）

> 📌 原本的三層（看見→感覺→建造）已升級為四段鏈條。設計細節見 [共視／共識機制設計](COVISION_METRIC_DESIGN.md)。

```
共視 → 共識 → 互補加速 → 指標是過程中的副產物
```

### 第 1 段：共視（Covision）

人和 Agent 指向同一個節點、知道彼此正在看什麼。

- 人看見 AI 的注意力在哪（機制：AI 注意力光暈）
- AI 感知人的意圖方向（機制：人意圖信號）
- 畫布是兩者注意力的交集場域

### 第 2 段：共識（Consensus）

理解對方為什麼這樣看、這樣選。

- AI 提議（機制：幽靈節點）→ 人接受/修改/拒絕
- 不是「你確定嗎？」（ConfirmDialog），是「我覺得可以這樣，你覺得呢？」
- 來回過程在畫布上展開，不是在對話框裡

### 第 3 段：互補加速（Complementary Acceleration）

各自補上對方的盲點，一起走到雙方都沒單獨想到的地方。

- 人補上：直覺、美感、脈絡、價值判斷
- AI 補上：資料、模式辨識、路徑探索、記憶檢索
- 合併的結果被標記為共視產物（`coCreated: true`）
- 比獨自做更快、更準、更有創意

### 第 4 段：指標是副產物（Metrics as Byproducts）

當共視／共識／互補真正在運作時，以下信號自然產生：
- 注意力重疊時間、共識往返次數、修改率、共視產物比例、首次提議接受率

**這些指標不需要額外的 tracker——它們是機制運作的日誌。** 先做好機制，指標就是讀 log。

## 3.1 原始三層定義（保留供參考）

<details>
<summary>展開原始三層定義</summary>

### Layer 1：共同看見（Co-seeing） → 現為第 1 段「共視」

最基本的層次。人和 Agent 指向同一個節點、知道彼此正在看什麼。

### Layer 2：共同感覺（Co-feeling） → 融入第 1-2 段

不僅看見同一個東西，而是對「這個東西正在變化」有同步的感知。

### Layer 3：共同建造（Co-shaping） → 現為第 2-3 段「共識 + 互補」

兩個意識各自貢獻自己的感知，在畫布上合併成雙方都沒有單獨想到的東西。

</details>

## 4. 共視與設計系統的關係

共視不是新增的設計能力。它是六種能力（清醒、貼近、可推演、有回應、不斷線、可沉浸）**合起來才產生的結果**。

| 設計能力 | 服務共視的什麼 |
|---|---|
| 清醒（xAI） | 讓人看懂 Agent 在做什麼 |
| 貼近（Raycast） | 讓人長時間停留在共視狀態不疲勞 |
| 可推演（Stripe） | 讓關係和過程可見，人與 Agent 看同一張圖 |
| 有回應（Figma） | 讓人的每一個操作都得到回應，Agent 的每一個狀態變化都被人看見 |
| 不斷線（Miro） | 讓共視的上下文不會因為切頁或縮放而斷裂 |
| 可沉浸（Active Theory） | 讓共視的重要瞬間——共識、門打開、橋建成——成為有情緒的場域 |

## 5. 共視的產品指標（未來方向）

當共視成為定位錨點，它也定義了橋樑應該追蹤的指標——不是「日活」「留存率」，而是：

| 指標 | 意義 |
|---|---|
| **共視時長（Covision Duration）** | 人與 Agent 在同一個畫布上同步注意力的時間。不是「使用時長」，是「真正共處的時間」 |
| **共同指向頻率（Co-pointing Frequency）** | 人與 Agent 在同一個節點上交會的次數 |
| **建造完成率（Co-shaping Completion）** | 由人與 Agent 共同產出、而非單方面完成的結果比例 |

這些指標區隔了橋樑與所有 workflow 工具：n8n 不追蹤共視時長，因為它沒有共視。

## 6. 共視作為開放社群的概念錨點

React 之於「宣告式 UI」，Git 之於「分散式版本控制」，橋樑之於**「人機共視」**。

當開源社群看到 Bridge，應該立刻抓到：

> **「啊，這是讓人跟 Agent 共處的那個工具。」**

共視不是 feature list 裡的一項。它是橋樑的**品牌動詞**——所有接觸橋樑的人（開發者、設計者、使用者、貢獻者）都應該在第一時間理解「這個工具的核心是共視」。

### 開源溝通建議

- README 第一句不寫「AI Agent Framework」，寫「The Covision App for Humans and AI」
- 貢獻指南第一條：「每一個 PR 都要回答——這讓共視更好了嗎？」
- 社群角色包、工作流卡的設計問卷第一題：「使用者和 Agent 如何在這個包裡共視？」
