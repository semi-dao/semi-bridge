> 關聯：docs/COVISION_MANIFESTO.md（共視）、agent.mind.beginWithEnd（以終為始——本稿即終點畫面的完整描繪）
> 技術前提：小橋偵察筆記 2026-09-18（引擎 canvasId final 錯定＝第一刀；單畫布掃描＋workspace 綁定＝第二刀）

## 一、設計理念（為什麼）

**現況的痛**：排程任務是「畫布裡的一個節點」——使用者要知道排程有沒有跑，必須打開那張畫布看節點。這違反「以終為始」：任務的價值在「使用者每天早上被提醒喝咖啡」，不在「工作流的形狀」。

**目標的樣子**：排程任務升級為**專案列表的一級公民**，與單次畫布專案並列。使用者一眼看到「哪些任務在為我自動工作、下次幾點、上次結果如何」——把無人值守的自動化變成**可看見的自動化**（Visible Automation），這也是開源差異化賣點。

**心智模型**：
- 🎨 單次畫布專案 = 我做的東西（被動容器）
- ⏰ 自動排程任務 = 為我工作的東西（活的主體，有節奏、有歷史、有產出）

---

## 二、資訊架構

```
專案頁（現有 project_door_page 擴充）
│
├── ⏰ 自動排程任務（新分區，排最上）
│   ├── [卡片] ☕ 早安咖啡提醒
│   │     每天 09:00 · 上次 ✓ 今天 09:00（音檔 94KB）· 下次 明天 09:00
│   │     [▶ 播放上次] [📂 開資料夾] [› 進入畫布]
│   └── [卡片] …（未來更多任務）
│
└── 🎨 畫布專案（現有門列表，原樣）
    └── 照舊
```

**分區規則**：一個專案（門）若含排程節點 → 同時出現在上區（以排程身份）；點「進入畫布」跳到同一張畫布。不是複製兩份資料，是同一張畫布的兩種視角（自動化視角 vs 編輯視角）。

## 三、任務卡片設計（終點畫面，逐項）

### 3.1 卡片本体（列表中的樣子）

```
┌─────────────────────────────────────────────────────┐
│ ☕  早安咖啡提醒                      [狀態燈 ● 綠]  │
│ 每天 09:00                                           │
│ 上次：今天 09:00 ✓ 成功 · 產出：語音 94KB            │
│ 下次：明天 09:00                                     │
│                                                      │
│ [▶ 播放上次]  [📂 開資料夾]  [⚙ 編輯]  [⏸ 暫停]    │
└─────────────────────────────────────────────────────┘
```

| 元素 | 規則 |
|------|------|
| 狀態燈 | 綠=最近一次成功 / 黃=從未執行（新任務）/ 紅=最近一次失敗 / 灰=已暫停 |
| 「上次」列 | 時間 ✓/✗ + 產出摘要（音檔大小/圖片張數/文字摘要前 20 字）——**產出可直接互動，不是路徑字串** |
| 「下次」列 | 引擎計算的下次觸發時間 |
| ▶ 播放上次 | 點了直接播最新一次產出（語音類）；圖片類直接開大圖預覽（複用 asset_preview） |
| 📂 開資料夾 | `open -R` 開 Finder 選中產出檔（任意門鐵則） |
| ⚙ 編輯 | 跳到該任務的畫布（編輯工作流） |
| ⏸ 暫停 | 暫停排程不停資料（= 現有 job 的 enabled 開關語意） |

### 3.2 點開卡片 → 執行歷史時間線（任務詳情頁）

```
☕ 早安咖啡提醒                          [⏸ 暫停] 
每天 09:00 · 建立於 09-16 · 引擎：App 層級（無人值守）

── 執行歷史 ──────────────────────────────
│ 今天 09:00  ✓ 成功   語音 94KB   [▶播放] [📂]
│ 昨天 09:00  ✗ 失敗   引擎掃錯畫布（canvasId bug，已修復於第一刀）
│ 09-16 09:00 ✓ 觸發   DAG 未執行（dagNodes 空殼，已修復於 1a5590b4）
└─ （更早…）
```

**設計細節**：
- 每次執行一列：時間 + 結果 + 產出 + 兩顆行動鈕（▶/📂）
- **失敗也誠實列出**（UI 誠實鐵則）——附一句當時的失敗原因，成為任務自己的「病歷」
- 歷史資料源：`schedule_triggers.jsonl`（daemon 已在寫）+ 新增執行結果落盤（見四）

### 3.3 觸發當下的即時通知

09:00 排程執行完 → App 內浮出 toast（右下，5 秒）：

```
⏰ ☕ 早安咖啡提醒 已執行 ✓   [▶ 播放] [› 查看]
```

點「播放」直接出聲（語音任務的最短路徑：從通知到聽見，一次點擊）。錯過 toast 的人看卡片「上次」列即可——雙保險。

## 四、資料層變更（技術規格摘要，給小橋的施工圖）

1. **引擎搬遷**：ScheduleEngine 從 canvas_v2_workspace 移到 App 層級（bridge_desktop_screen 或獨立 service locator）——脫離 UI 生命週期，App 活著引擎就活著
2. **掃全庫**：`_scanAndFire` 從 `getCanvasNodes(canvasId: X)` 改為掃全庫 schedule 節點；canvasId 降級為分類標籤
3. **執行結果落盤**：新增 `schedule_runs.jsonl`（或 DB 表）：`{jobId, firedAt, success, outputType, outputPaths[], summary}`——列表的「上次」列與歷史頁的資料源。daemon 觸發紀錄（jsonl）保留，但執行結果由引擎寫
4. **產出歸位**：排程產出的檔案統一進 `Application Support/farm.semiwasabi.bridgeApp/schedule_outputs/<jobId>/`——任意門有穩定的落點，不再散在深層快取
5. **現有相容**：門（ProjectDoor）含排程節點者自動獲得雙重視角，無排程的門照舊；`schedule_jobs.json` 格式不動（daemon 已穩定跑三天）

## 五、實作順序（訓練關卡拆分，每關一個終點畫面）

| 關卡 | 內容 | 終點畫面 | 驗收 |
|------|------|---------|------|
| W1 | 引擎搬遷＋掃全庫（純技術，UI 不變） | 使用者無感，但 App 停在 home 頁排程照跑 | 手動 2 分鐘觸發實測 |
| W2 | schedule_runs 落盤＋產出歸位 | jsonl 有真實執行紀錄＋檔案在固定資料夾 | ls + cat 實證 |
| W3 | 專案頁「自動排程」分區＋任務卡片 | **Blue 在專案頁看到咖啡任務卡片（狀態燈綠、上次成功、▶ 可播）** | Blue 親測 |
| W4 | 執行歷史時間線＋失敗誠實列 | 點開卡片看到三天來的執行史（含兩次已修復的失敗） | Blue 親測 |
| W5 | 觸發即時 toast 通知 | 09:00 浮通知，一鍵播放 | 隔日實測 |

W1–W2 給小橋（技術練手），W3–W5 也在他能力射程內（asset_preview 複用），但每關都要走「終點畫面描述 → Blue 確認 → 動手 → 實物錨定」的乒乓流程。
